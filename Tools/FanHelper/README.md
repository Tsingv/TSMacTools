# Optional fan helper

The app can read available AppleSMC sensors without this helper. Manual fan control requires this root LaunchDaemon, supported hardware, a matching signed app, and explicit opt-in in Settings → Fans. It is development code awaiting hardware validation. The implementation has been built and tested with fake I/O; the install script has not been executed during development.

The supported hardware path requires `FNum`, `F<n>Ac`, `F<n>Mn`, `F<n>Mx`, `F<n>Tg`, and per-fan `F<n>Md` keys. Target values must use `fpe2` or `flt `; mode must use `ui8 `. Shared `FS! ` mode masks are deliberately unsupported. AppleSMC access, key names and write permissions vary between models and OS releases; Apple Silicon may expose different or fewer temperature keys. Fanless Macs and unsupported models cannot enable control. The app reports errors rather than guessing layouts.

Build the app with `./build.sh` (Debug) or `./build.sh --release`. The Xcode app build phase compiles Core statically into the hardened helper, signs it with SurTeamCode, and embeds it at `Contents/Library/LaunchServices/TSMacToolsFanHelper` before signing the app. The installed app needs no repository checkout or build tools. `Tools/FanHelper/build.sh` remains a standalone build diagnostic; it does not install anything.

Open Settings → Fans and click **Install helper…**, **Reinstall…**, or **Uninstall…**. These explicit buttons show the macOS administrator authorization dialog. Viewing Settings, launching the app, and **Check helper again** never request administrator authorization. Cancellation and operation failures appear in the page. Accessibility permission is separate and does not authorize SMC writes.

The app copies the bundled executable into root-private staging and verifies its exact identifier and pinned SurTeamCode leaf certificate SHA-1 `85B37EA8D5B9719CB5F443613573AD1F4986B17B` before executing its fixed management operation. The signed implementation checks root ownership, file types, permissions and symlinks, verifies the published executable, and generates fixed launch arguments. It accepts no arbitrary paths, shell commands, SMC keys, or launch arguments. Both XPC peers retain the same exact certificate and identifier requirements. No library-validation exception or Team ID is used.

Reinstall and uninstall request automatic mode, stop the existing service through launchd, and confirm restoration again before replacement or removal. Restoration failure stops the operation and reports an error. A failed bootstrap leaves the installed files available for a retry. Installation starts the daemon, whose startup also restores before accepting clients. Do not install on a machine whose manual mode must be preserved. The page separately reports disk installation verification, service running PID when available, and the authenticated `ready-v1` XPC handshake. Only a successful handshake enables the apply checkbox.

Live RPM and temperature readings should appear. The apply checkbox remains disabled unless the helper handshake succeeds. Opt in only after checking sensor identity and firmware fan limits on the device. Raw temperature keys remain visible because CPU/GPU aliases are heuristic. Curve changes apply on the next one-second sample. Missing required sensor readings request automatic mode. Leaving the Fans page, closing Settings, unchecking apply, or disconnecting requests automatic mode. Reopening requires new opt-in.

The helper accepts one signed client, validates each fan ID/percentage, derives RPM from fresh firmware limits, writes the target and mode, and checks readback. A five-second lease is renewed by each valid demand; a 250-ms timer restores automatic mode after expiry. Readback verifies requested register values, not physical fan convergence. Power notifications restore before acknowledging sleep, and wake restores before accepting demands. Failed restoration is retried on timer ticks where an active lease remains. Launchd restarts after helper crashes and startup restores before accepting connections. A killed/stalled helper, kernel failure, or inaccessible SMC can delay restoration; this is not a firmware watchdog or a guaranteed thermal safety mechanism.

Device acceptance checks: verify sensor units/identity against a trusted monitor; confirm real RPM stays inside firmware limits; apply a conservative curve; disconnect the app and check automatic-mode readback within the lease; test sleep/wake; test orderly helper stop/restart; check no request can target unknown fans or arbitrary SMC keys. Test unsupported hardware rejection. These checks have not been performed by the implementation agent.

To remove the helper, click **Uninstall…** in Settings → Fans. Recheck status afterward. Manual acceptance must cover fresh install, reinstall while running, uninstall, a denied/cancelled prompt, unsafe destination paths, an invalid bundled or installed signature, stopped service, rejected peer, and bootstrap/restore failure. No helper installation, administrator operation, or hardware write was executed during implementation.

Rule edits require the bundled `ready-v2` helper protocol. Reinstall an older installed helper using the explicit Settings button. Each request replaces the complete active fan demand set, releasing removed targets immediately. The master control switch persists `fans.enabled` across app launches; rule enable switches only select participating rules.

Helper updates: installing a new app updates its bundled helper but never silently replaces the privileged running service. Fans settings compares the pinned-signature-validated installed and bundled executable CDHashes off-main, shows abbreviated hashes, and independently checks the authenticated running protocol (`ready-v2` / `unavailable-v2`). A content mismatch, missing fingerprint, or incompatible protocol disables master control and labels the existing replacement action **Update helper…**. One explicit administrator-authorized click uses the existing restore-before-replacement management flow, then refreshes fingerprints and the handshake; the persisted automatic-rules preference is reapplied. Matching content does not trigger reinstall, and launch/check operations never request administrator authorization. Hash prefixes are display-only; comparison uses the complete CDHash. Hardware unavailability under the current protocol is reported as a hardware error rather than an update requirement.

Automatic fan rules use the persisted `fans.enabled` preference, disabled by default and for legacy configurations. Once enabled, AppDelegate starts one FanRuntime at launch and reconfigures it on saves and configuration reloads. The runtime owns the serial reader, single authenticated helper connection, snapshots and complete demand batches; Settings only displays its monitoring view and edits configuration. Closing Settings or changing tabs leaves rules active. Missing/outdated helpers block application without administrator prompts. Sleep suspends demand and clears the snapshot; wake requires a fresh reading. Exit requests automatic restoration and waits up to 1.5 seconds; independent helper disconnect handling and five-second leases remain the fallback.
